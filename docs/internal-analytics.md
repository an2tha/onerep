# Internal analytics

Open `/admin/analytics` in the existing app. An Analytics entry appears in More only for allowed admins. Product metrics use Convex records without additional client tracking. TikTok and Instagram share one tabbed social section, with separate date selections preserved when switching tabs. Verified values, including genuine zeros, remain visible. Missing metrics stay in a collapsed disclosure and appear automatically when verified data arrives. Empty charts and unverified top-content lists are hidden; follower growth charts require dated boundary observations. Social metrics use private snapshots of OneRep's Metricool analytics.

## Local access to production data

Run `bun run analytics:local` from the repository root, then open <http://127.0.0.1:5173/admin/analytics>. This starts the existing app on the loopback interface and points it at the production Convex deployment (`chatty-panda-144`). It does not publish the frontend. The local server overrides the development backend settings for its process only and disables the existing Umami tracker. Port 5173 is already a trusted auth origin. A stored custom-server override in the browser takes precedence; use the login screen's Server control to select OneRep Cloud if needed.

The backend analytics functions must be deployed to production separately. Sign in with an allowlisted account. Email-based admins must register and verify their email before access is granted. The login redirect returns to the dashboard after sign-in. Keep the local server running while using the dashboard.

Set these **server-side Convex environment variables** on each deployment:

- `ANALYTICS_ADMIN_USER_IDS`: comma-separated canonical token identifiers, formatted as `<CONVEX_SITE_URL>|<Better Auth user _id>`. Use the existing internal `maintenance/seed:userIdForEmail` query to resolve an account email, then copy its `userId`.
- `ANALYTICS_ADMIN_EMAILS`: optional comma-separated admin email addresses, case-insensitive. Access requires a valid Better Auth session, a matching canonical identity, and a verified email on the stored account. A JWT email claim alone never grants access. This can reserve access before an account is registered. When both admin allowlists are empty, everyone is denied.
- `ANALYTICS_EXCLUDED_USER_IDS`: additional test account token identifiers.
- `ANALYTICS_EXCLUDED_EMAILS`: additional exact test account email addresses, case-insensitive.

Reserved `.test`, `.invalid`, `localhost`, and `example.com`, `example.net`, `example.org` domains (including subdomains) are always excluded. Explicit exclusions cover test accounts using real email providers. Admin accounts are included unless separately excluded. No account list or exclusion editor is exposed in the dashboard.

## Definitions

- **Total signups**: retained Better Auth user records, including accounts that never completed onboarding, excluding test accounts. Uses the original auth `createdAt`, not preferences creation or first workout. Deleted accounts and earlier identity-provider history cannot be recovered from these records.
- **Logged a workout**: distinct eligible accounts with at least one `workoutLogs` row. Legacy rows without session IDs count. A health-store import alone does not count; an explicit promotion into the training log does.
- **Logged on 2+ days**: distinct eligible accounts with at least two different valid `workoutLogs.date` values. Two sessions on one date count as one day.
- **Workout-active, 7/30 days**: distinct accounts with a workout log created in the rolling 168/720 hours ending at the report cutoff. Uses immutable `_creationTime` because this measures logging activity. `completedAt` describes when training happened and may be backdated; editing a log does not create another activity event.
- **Comparisons**: the same user-count calculation over the immediately preceding, non-overlapping 7-day or 30-day window. Changes are absolute user counts, not percentage changes. New signup counts use account creation timestamps.
- **Weekly growth and activity**: 26 Monday-based UTC weeks, with 8, 12, or 26 weeks selectable. Each eligible account is counted once per week for activity, even if it logs multiple workouts. The current calendar week is partial. Unknown values are marked with `?` in the chart and “Unavailable” in the numeric view.
- **Signup-to-repeat funnel**: all retained accounts, accounts with any saved workout, and accounts with two distinct workout dates. This is lifetime recorded conversion, separate from the cohort activation window.
- **Cohorts**: signup calendar weeks, Monday through Sunday in UTC. Activation is at least one log created in `[signup, signup + 7 days)`. Retention is an activated user with another log in `[signup + 7 days, signup + 14 days)`, divided by activated users. Rates wait until the entire signup week has completed the relevant observation period. No activated users yields an undefined retention rate, displayed as “No activated users”, not 0%.

The cohort summary rates divide the summed numerators by the summed denominators across mature, available cohorts. They are not averages of cohort percentages. The latest 12 cohorts appear initially, with an option to show older cohorts. Metric definitions and coverage notes are collapsed under “About these metrics”.

## TikTok

The connected source is Metricool brand `7632357`, TikTok `@onerep.life`, reporting in `Europe/Berlin`. The dashboard reads a single brand-level cache record from `analyticsSocialSnapshots` through the admin-only `analytics:tiktokSnapshot` query. The private `analytics:syncTikTokSnapshot` mutation validates and replaces that record. It can be called only by server code or the authenticated deployment-admin CLI. There is no public browser write or Metricool credential in the frontend. The table is classified as global business data, not OneRep user data.

The daily 9am Berlin summary fetches Metricool and writes this snapshot after a successful fetch. Keep the automation enabled for ongoing updates. Refresh in the dashboard reads the cached snapshot; it does not call Metricool. The panel displays its sync time and labels snapshots older than 36 hours. Provider failures preserve the previous good snapshot rather than making it appear fresh.

Each snapshot holds yesterday, the last seven complete calendar days, and the last thirty complete calendar days, plus the latest dated follower observation. Each window counts videos published within its dates and sums their **cumulative video totals**, not views or interactions occurring within those dates. View-based engagement is `(video likes + comments + shares) / video views * 100`; it is unavailable with no views. The three top videos come from that publishing window and their links have tracking parameters removed. Captions render as text. Metricool's native reach-based engagement is a different calculation and is not substituted for this view-based rate.

Published-video history became available during initial setup. Account evolution rows remain sparse, so period-wide account views, net follower change, and profile views are marked unverified and stored as `null` until coverage can be established. Unknown values never become zero. A confirmed publishing window with no videos can show genuine zero. Profile-link visits and TikTok-to-signup attribution are unavailable.

Use `convex/lib/tiktokAnalytics.ts` as the authoritative snapshot payload contract. There are exactly three windows and at most three top videos per window. Unsafe URLs, unrelated accounts, invalid counts, malformed dates, and older snapshots are rejected. Do not send OneRep user, health, or workout records to Metricool.

Charts use an optional bounded history of 61 consecutive dates: 60 complete days for equal-length current/previous publishing periods, plus the preceding follower baseline. `videoViews` sums cumulative views of videos published on that date, not views received that day. `followers` stores only genuine dated observations. Missing values remain null, follower lines never bridge missing days, and the daily table exposes the underlying observations. View comparisons require complete values for both periods. Percent changes are omitted when the previous total is zero. Follower growth requires observed counts on the day before the period and on its final day, with the same requirement for the prior-period comparison. Sparse history therefore shows observations without inventing growth. The daily sync reads 60 days of posts and 61 days of follower history, retaining previous genuine observations only on their original dates.

## Instagram

Metricool brand `7632357` also connects Instagram `@onerep_app`. The admin-only `analytics:instagramSnapshot` query reads its separate `analyticsInstagramSnapshots` brand cache, classified as global business data. Only internal `analytics:syncInstagramSnapshot` writes it. There are no browser credentials or public writes. The daily 9am Berlin automation refreshes it independently of TikTok, preserves the last good snapshot on provider failure, and includes Instagram in the daily summary.

The payload contract is `convex/lib/instagramAnalytics.ts`: exactly three publishing windows, at most 61 consecutive history dates, and at most three public content links per window. Feed posts and reels use their separate Metricool connectors, deduplicated by URL. Organic cumulative views use `IGPO28` for feed posts and `IGRE23` for reels. Interactions include likes, comments, saves, and shares. View-based engagement divides these interactions by known positive content views. Stories, paid content, all-account views, and summed reach are excluded. Deprecated video-view and profile-click fields are not substituted. Charts group cumulative views by publish date and compare equal publishing periods. Follower counts use dated `IGEV01` observations; growth needs exact boundary observations, and missing dates remain blank.

At setup on 24 October 2026, Metricool supplied 4 followers as of 23 October but empty post and reel responses and sparse account activity. Those initial empty responses do not establish zero historical publications. Content totals and chart history therefore remain `null` with coverage `unverified` until source completeness is established. Confirmed empty publishing windows may subsequently display zero. The panel shows source and sync dates and flags snapshots older than 36 hours.

All results describe retained records, not a complete event ledger. Imports that recreated documents may reset creation timestamps. Deleted logs, deleted accounts, historical app visits, and activity under identities that cannot be linked to current auth accounts are unavailable. Unlinked workout records are excluded because their test status cannot be established. The dashboard reports that exclusion count. Missing or malformed historical dates produce `null` for affected calculations, rendered as “Unavailable”. A complete observation window with no matching retained records produces zero. An immature window produces “Pending”. Accounts without usable signup dates count in totals but not cohorts.

## Operation and privacy

Reports are calculated on demand with a fixed creation-time cutoff, using bounded internal pages rather than full-table subscriptions. Refresh reruns the calculation. Pages read existing records without creating analytics copies. Only account IDs, dates, and log creation times reach the server-side reducer. Only aggregate counts, cohort weeks, and data-quality counts reach the browser. No names, emails, exercises, durations, or health values are returned by the public report.

Every page and the public report independently enforce the admin allowlists. Token identifier entries require the authenticated canonical identity; email entries additionally require a live session and the stored account's verified email. The report rechecks access before returning. The UI guard is supplementary. Changes or deletions during the paginated scan can appear on the next refresh; this is not a cross-page transactional snapshot. The scan caps each source at 2,000 pages and fails explicitly if the cap is reached, never returning truncated totals. Larger deployments should move to a server-side aggregate and backfill rather than raising this cap indefinitely.
